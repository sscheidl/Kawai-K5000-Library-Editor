# Audit — KA1 parser and KAA extraction

**Review target:** commit `dd66e53` (as handed over), audited at `ef21c63`,
branch `main`.
**Audited:** 2026-09-12.
**Auditor:** Claude Code, in place of the Codex review commissioned in
[`CODEX_HANDOFF.md`](CODEX_HANDOFF.md), which never reported.
**Corpus:** the private reference corpus (963 `.KA1`, 76 `.KAA`), extracted
read-only from `K5000_Presets.zip`. Every figure below was re-derived from it.

## Method, and its one weakness

The handoff says not to trust the code comments, the README, the commit
messages, the test names or its own numbers. So none of them were used as
evidence. Every quantitative claim was re-derived with a Python model written
from the format description alone, deliberately without reading
`tools/research/` — which is itself under audit and would have made the check
circular. That model agrees with the C++ parser and with the committed manifest
on every figure, which is three implementations agreeing rather than two.

The weakness is worth stating plainly: the same author reviewed the same work.
An independent reviewer remains preferable and this does not substitute for one.
What it does substitute for is an indefinite freeze on a subsystem that blocks
the rest of the roadmap.

## Verdict

The claims hold. Six confirmed defects, none in the format rules themselves —
they are in the harness that is supposed to prove those rules, and in the one
place that writes files. Two are P1.

| # | Severity | Area | Status |
| --- | --- | --- | --- |
| F1 | P1 | Golden corpus loader drops unreadable files in silence | fixed |
| F2 | P1 | `k5000cli extract` renames an unverified write into place | fixed |
| F3 | P2 | `computeChecksum` fabricates `0` for input it cannot sum | fixed |
| F4 | P2 | Two golden tests assert nothing that can fail | fixed |
| F5 | P3 | Base-address rationale unsupported; wrong base had no bank-level signal | fixed |
| F6 | P3 | `k5000cli extract` TOCTOU between `exists()` and `rename()` | documented |

## Claims, re-derived

### 1. The checksum rule and its scope — **confirmed**

`(sum(payload[1 .. 82 + 86*S)) + 0xA5) & 0x7F`, ADD wave kits excluded.

| Measure | Re-derived | Claimed |
| --- | --- | --- |
| Structurally complete KA1 files | 937 | 937 |
| Patch checksum passes | 937 | 937 |
| Patch checksum fails | 0 | 0 |
| Files failing an ADD-kit checksum | 4 | 4 |

The `subspan(1, end - 1)` arithmetic is correct: it sums `[1, 82 + 86*S)`, which
is what the documentation says.

The scope claim is not merely consistent with the corpus, it is discriminated by
it. Summing the ADD wave kits as well drops the pass rate from 937 to 133 — and
those 133 are the files that have no ADD kit to include. The exclusion is
established, not assumed.

The four kit-checksum failures (`Harsh.ka1`, `ICEARP.KA1`, `SIDBass1.KA1`,
`SIDComp1.KA1`) all pass their *patch* checksum. Treating them as corrupt kit
data inside otherwise sound patches is the reading the evidence supports.

`computeChecksum` returning `0` for a too-short payload is real, but not
reachable from `parse()`, which bounds-checks first. Fixed anyway — see F3.

### 2. ADD/PCM classification — **confirmed**

Wave kit number at source-relative `+28/+29`, high byte first, `512` = additive.

The decode `(hi << 7) | lo` is sound here: **no byte at `+29` has bit 7 set**
anywhere in the corpus, so the two fields never overlap. Nor can a stray high
bit manufacture an additive source — `(hi << 7) | lo == 512` has exactly one
solution, `hi == 4, lo == 0`.

"One corpus file contradicts the file-length cross-check" is confirmed as
exactly one: `Rasty.KA1`, wave 8186, length implying 3 ADD sources against
descriptors implying 2. Reported `StructurallyAmbiguous`, not guessed.

Out-of-range wave values are *not* unique to that file — 12 occurrences across
11 files. The other 11 files are already `Malformed` on length grounds, so
`FORMAT_NOTES.md`, whose stated scope is the 938 analysed files, is accurate.

The unexplained PCM clustering holds exactly within that scope: 341..463,
nothing below 341. Values below 341 (0, 1, 41, 64, 69, 70, 192) occur only in
files that fail the structural traversal, so they are not evidence about the
numbering.

### 3. Structural length, and Invariant A — **confirmed, and the tests bite**

No arithmetic on two pointers can reach a size: `structuralSize` comes only from
`patchSize(S, A)`.

The handoff is right to ask whether the `[invariant]` tests actually fail. They
were tested by mutation — pointer-delta sizing was reintroduced in
`kaa::extractSlot`, and both tests failed. They are regression tests, not
decoration.

Two *other* tests were decoration, and the same mutation proved it. See F4.

Gaps are never included in a payload: the extracted extent is
`bytes.first(structuralSize)`, and the corpus check for overlapping spans passes
across all 76 banks.

### 4. KAA pointer mapping — **confirmed, with a documented residual risk**

`file_offset = 0x0E04 + (pointer - base)`, `base` = smallest non-zero pointer.

| Measure | Re-derived | Claimed |
| --- | --- | --- |
| Banks | 76 | 76 |
| All exactly 134 660 bytes | yes | yes |
| Occupied slots | 4072 | 4072 |
| Patch checksum passes at the computed offset | 4072 | 4072 |
| Fragmented banks | 8 | 8 |
| Slots with a stale ADD-kit pointer | 28 | 28 |
| Extracted payloads byte-identical to a standalone KA1 | 2210 | 2210 |

On the direct question — can a stale kit pointer drag the base below the true
data start? — the measurement is that **including ADD-kit pointers changes the
base on 0 of 76 banks**, and structurally it never can help: a live slot's kit
pointers address bytes inside its own patch and therefore always exceed its
patch pointer. Only a stale pointer could move the base, and only downwards,
which is the wrong direction. The scan was left as written, because narrowing it
is equally unproven and the corpus cannot distinguish the two.

The real fragility is elsewhere, and the handoff did not ask about it: the base
is a *heuristic*, not a value read from the file. It assumes the lowest address
still referenced is where the data region begins. Delete the first-allocated
patch and that assumption fails — every offset in the bank shifts, and because
the deleted patch's bytes are still physically present, slots can still parse
cleanly and fail only on the checksum. No corpus bank does this. Addressed by
F5 rather than left as a footnote.

`Bank::fileOffset` is correct at both ends: `pointer < base` and
`relative >= 0x20000` are both rejected, so the returned offset is always inside
the file. Nothing reads `bytes[offset]` unguarded — the stale-pointer scan in
`parseBank` checks `sourceCountOffset >= bytes.size()` first.

### 5. Bounds safety — **confirmed**

Every read in `ka1::parse` is guarded before it happens. Specifically
`waveOffset + 1` for the last source lands at `82 + 86*S - 57`, inside the
`82 + 86*S` already required; the kit subspans lie inside the `structuralSize`
already required. `kaa::extractSlot` bounds parsing by the rest of the file, so
a corrupt source count cannot reach past the end.

The handoff asked for fuzzed and truncated input, and no such test existed. Two
were added: every prefix of a well-formed patch (`[ka1][fuzz]`), and 2000 seeded
byte-damage mutations. No crash; the payload invariants hold on every survivor.

### 6. Source-file safety — **confirmed, one real defect**

Nothing in `tools/research/` opens a corpus path for writing; the single write
in that tree is `make_manifest.py` writing its own output file. The
`[golden][safety]` test re-checks the size and mtime of all 1039 corpus files
after a full parse run.

`k5000cli extract` refuses to overwrite and leaves no `.partial` behind —
verified live: a second run over the same directory wrote 0 and skipped 60, with
no leftovers. End-to-end, the 60 extracted files are SHA-256 identical to the
independent Python extraction.

But the write itself was not verified before being promoted — F2.

### 7. Verification honesty — **confirmed**

`GoldenTested` is justified and is not overclaimed: the evidence string in
`ka1::support()` states in its own words that the tests skip without a corpus,
so the level does not silently rest on a public CI run that never exercised it.

No write path bypasses `Unsupported`; the only file-creating code is
`k5000cli extract`, which copies bytes and never serializes.

The manifest cross-check is not circular. `make_manifest.py` derives its
expectations from the Python model in `k5000_probe_lib`, not from the C++
parser. This audit's own model, written independently of both, agrees with them
on every figure.

## Findings

### F1 — the golden corpus loader drops unreadable files in silence — P1

`tests/golden/test_corpus.cpp`, corpus loader: a file that matches by extension
but cannot be opened hits `if (!stream) { continue; }` and disappears. No count,
no warning, no failure.

This is not hypothetical. On this machine the extracted corpus sat behind a path
long enough that four commercial banks — `SESSION.KAA`, `BassLead.KAA`,
`Classic.KAA`, `PadsComp.KAA` — exceeded `MAX_PATH`. The suite read 1035 of 1039
files and reported **100% passed**. Every golden test draws its authority from
"this holds across the whole corpus"; that sentence had quietly become false.

The manifest test's row-count guard did notice the discrepancy, and responded by
skipping itself — turning the one available signal into a non-event.

**Fix:** unreadable paths are collected, and a new `[golden][safety]` test fails
on any of them. Verified in both directions: it fails with the long path
(`unreadable: 4`) and passes with a short one.

### F2 — `extract` renames an unverified write into place — P1

`src/cli/main.cpp`, `commandExtract`: the stream was checked *before* the
`ofstream` went out of scope. Writes are buffered, so a full disk or a failing
device surfaces during the flush in the destructor — which nobody looked at. The
truncated `.partial` was then renamed into place, counted as written, and
reported as success. The resulting file is a plausible-looking KA1 that is
short, in a project whose entire premise is byte-exactness.

**Fix:** `close()` before the check, and the file is read back and compared
against the payload before the rename. Extraction is the one place this tool
creates a file a user will later treat as an original.

### F3 — `computeChecksum` fabricates a checksum — P2

`src/formats/ka1/Parser.cpp`: returned `0` when the payload was too short or the
source count impossible. `0x00` is a legal Kawai checksum, so the caller cannot
tell a computed value from a refusal.

Not reachable from `parse()`. Worth fixing now, while the only callers are
`parse()` and one test, rather than after a serializer exists.

**Fix:** both helpers return `std::optional<std::uint8_t>`. `parse()` uses
`.value()` at the one call site where the structural checks have already
guaranteed a result.

### F4 — two golden tests assert nothing that can fail — P2

Found by mutation. With pointer-delta sizing reintroduced:

| Test | Assertion | Clean | Mutated | Caught? |
| --- | --- | --- | --- | --- |
| extracted patches are byte-identical | `identical > 0` | 2210 | 2184 | no |
| fragmented banks do not leak padding | `fragmentedBanks >= 0` | 8 | 0 | no |

The second is the worse of the two. `>= 0` is a tautology, and it hid the
sharpest signal available: sizing from the pointer delta makes every span
exactly adjacent, so the fragmentation count collapses to 0 and the overlap
check inside that test can never fire again. The test that exists to prove
fragmentation is handled becomes vacuous precisely when it stops being handled.

**Fix:** both figures are pinned when the corpus is the one they were measured
on (2210 identical, 197 differing, 8 fragmented banks), with
`fragmentedBanks >= 1` holding unconditionally. Re-running the mutation now
fails both tests.

### F5 — the base-address rationale, and the missing signal — P3

`Bank.h` justified scanning ADD-kit pointers with "a stale kit pointer can still
be the lowest address the bank ever used". That is a description of the failure
mode, offered as the reason. The corpus does not support it: the scan changes
the base on 0 of 76 banks.

Separately, a wrong base produces up to 128 individual checksum mismatches and
no statement of the shared cause.

**Fix:** the comment now records what was measured, including why narrowing the
scan is equally unproven. `ExtractionResult::baseAddressSuspect` and a
`BankBaseAddressSuspect` diagnostic fire when every readable slot fails its
checksum — with a two-slot minimum, so a single damaged patch is still reported
as a damaged patch. Two regression tests cover both sides.

### F6 — `extract` TOCTOU — P3, documented

Another process could create the target between `exists()` and `rename()`, and
`std::filesystem::rename` replaces an existing file. Closing this needs a
platform-specific exclusive-create rename. Accepted for a diagnostic tool and
commented at the site; it should not survive into the GUI's export path.

## Not defects

- `usedBytes()` reports `endOfDataPointer - baseAddress`, the bank's own figure,
  which in 5 banks exceeds the highest patch end by 2 bytes. The header says it
  is the bank's claim rather than a measurement, which is the honest framing.
- Source counts `0` and `127` in the corpus are rejected before anything else is
  read, as documented.
- The `+2` trailing-byte pattern appears in both standalone files and bank
  end-of-data pointers. Unexplained, harmless, already recorded.

## Reproducing this audit

```bash
cmake --preset core-only -G "Visual Studio 17 2022" -A x64 \
      -DK5000_REFERENCE_CORPUS="<short path to an extracted corpus>"
cmake --build build/core-only --config Debug
ctest --test-dir build/core-only -C Debug --output-on-failure
```

44 tests, all passing, with the corpus configured and without it. Use a **short**
corpus path on Windows — and if you cannot, F1's test will now tell you.
