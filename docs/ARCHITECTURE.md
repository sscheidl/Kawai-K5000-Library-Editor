# Architecture

## Layering rule

```
        ┌──────────────────────────────────────────┐
        │  src/app      desktop entry point        │
        ├──────────────────────────────────────────┤
        │  src/gui      Qt 6 Widgets               │  ← no binary parsing here
        ├──────────────────────────────────────────┤
        │  src/library  scanning, import/export    │
        │               orchestration, indexing    │
        ├──────────────────────────────────────────┤
        │  src/formats  ka1 kaa kc1 kca sysex      │  ← no Qt types here
        │  src/disk     fat12 / IMG                │
        ├──────────────────────────────────────────┤
        │  src/core     canonical model, commands, │
        │               undo/redo, diagnostics     │
        └──────────────────────────────────────────┘
                        ▲
        src/cli  ───────┘   same core, no GUI
```

Two hard boundaries, both enforceable by review and by the fact that `src/cli`
must keep linking:

1. **The GUI contains no serialization or parsing code.** It calls commands and
   renders model state.
2. **Core and format libraries do not depend on Qt GUI objects.** If a Qt utility
   type is ever needed below the GUI layer, that is a decision to record here
   first, not an incidental include.

## Canonical model (specification §4)

A `Single` may originate from a KA1 file, a slot inside a KAA bank, an individual
SysEx message or a bank SysEx dump. All of these map to **one** canonical in-memory
`Single`, which retains enough provenance to diagnose problems:

- parsed semantic data
- the original raw payload
- preset name
- source composition
- serialized size
- originating file
- originating container
- original slot
- validation state

`Multi` follows the same shape. Unknown and reserved bytes are carried through
untouched — the model never normalizes data merely because it is not understood.

## Command system (specification §15)

Every workspace mutation goes through a transactional command object. Keyboard,
context menu, toolbar and drag-and-drop must all dispatch the *same* command —
there is no second, parallel implementation for any entry point. This is the
mechanism that makes Undo/Redo correct rather than approximately correct.

`Cut` never destroys the source. Removal happens only as part of a successful
paste/move transaction.

## Threading

Directory scanning, parsing and image writing run off the GUI thread with progress
reporting and cancellation. The model is mutated on the GUI thread from completed
results, so command history stays single-threaded and deterministic.

## Output validation (specification §25)

Every serializer has a matching parser, and no operation reports success before
the round trip has been verified:

```
model → serialize → parse the generated bytes → validate → compare semantics
```

For images: `image model → serialize → reparse → validate FAT12 → enumerate → verify contents`.

## Version 1.5 headroom

MIDI is not implemented in V1, but nothing in the model may make it impossible.
Transfer-oriented concerns (bank/slot addressing, SysEx framing, transfer queues)
belong to a future `src/midi` sibling of `src/formats`, consuming the same
canonical model.
